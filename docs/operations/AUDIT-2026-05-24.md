**Audit date**: May 24, 2026  
**Auditor**: Remy (AI Producer) with Explore and documentation-auditor subagents  
**Scope**: Full clean-slate audit across all domains — GitHub, runtime, CI/CD, security,
backend, frontend, database, metadata, library management, deployment, dependencies,
documentation, and custom tooling.  
**Evidence sources**: Live GitHub API (issues, PRs, Actions), runtime application logs

## Executive summary

The project is in a healthy Phase 5/6 posture overall, with strong security baseline,
clean CI/CD supply chain, and complete Dual-Format Tracking delivery (DF-1 through DF-16).
Three critical operational issues require immediate attention before Phase 6 exit:

1. A download loop has been running continuously for **34+ days** — one item stuck in
   qBittorrent is processed every 90 seconds without ever completing import.
2. Dependabot PR [#70](https://github.com/Swartdraak/Bibliophilarr/pull/70) proposes a
   `Microsoft.AspNetCore.SignalR.Client` 8.0.11 → 10.0.7 jump against a .NET 8 project —
   merging it would break the build.
3. A disk-scan run in April logged `files=517 (filtered=517), identified=0` — all 517
   discovered files were filtered, yielding zero imports. This warrants investigation.

A queue of 19+ Dependabot PRs (as of May 2026) targeting `main` needs structured triage.

## Domain 3: Runtime — Application logs and library management

**Evidence**: `/home/swartdraak/.config/Bibliophilarr/logs/bibliophilarr.{0..5}.txt`
and `.debug.{0..49}.txt`. Log level configured to `debug`.

### Critical: stuck download loop

**Finding 3-A (CRITICAL)** — `Ellen.Hopkins.Impulse.2008.RETAiL.EPUB.eBook-NODE` has
been processed by `DownloadProcessingService` every 90 seconds without success since at
least **April 20, 2026** (34+ days at the time of audit). Every polling cycle returns:

```
ImportDecisionMaker|Import run complete: files=0 (filtered=0), releases=0, identified=0
```

The path is correctly remapped by `RemotePathMappingService`:

```
Remapped /downloads/ebooks/Ellen.Hopkins.Impulse.2008.RETAiL.EPUB.eBook-NODE
→ /media/torrents/ebooks/Ellen.Hopkins.Impulse.2008.RETAiL.EPUB.eBook-NODE
```

Root cause candidates (in priority order):

1. The directory exists in qBittorrent's completed downloads but is empty on the local
   mount — the EPUB file was manually moved or deleted after download.
2. The item is seeding indefinitely with files accessible to qBittorrent but the mapped
   local path does not exist from Bibliophilarr's perspective.
3. A race condition in `CompletedDownloadService` where the item cannot transition to
   `Imported` or `Failed` because the file count is zero, so it stays `Completed`.

**Immediate operator action**: In qBittorrent, check whether the torrent has any files
present. If files are missing, remove the torrent from qBittorrent. This will stop the
download loop in Bibliophilarr on the next poll cycle (within 90 seconds).

**Longer-term fix**: `CompletedDownloadService` should detect zero-file completed
downloads as a terminal failure state (`DownloadItemStatus.Failed`) after N retry
cycles and stop re-queuing them. This is a new GitHub Issue.

### Disk scan: zero match rate

**Finding 3-B (HIGH)** — The April 23, 2026 disk scan logged:

```
files=517 (filtered=517), releases=0, identified=0 (perfect=0, good=0, poor=0, unmatched=0)
match_rate=0.0%
```

All 517 discovered files were filtered before identification. Possible causes:

- The quality profile minimum page count or format filters are excluding all files.
- The metadata profile filtering is removing all books from consideration before
  file-level matching runs.
- All files are already tracked in the database and the filter is correctly skipping
  them (check `DiskScanService` `filtered=N` logic — it may filter already-imported
  files, which is correct behavior not a bug).

The log context immediately preceding this was `RefreshAuthorService|Updating Info for
Zogarth` and `MetadataProfileService|Popularity filter removed 85% of 95 books`.
The high filter rate during a refresh scan is likely correct (files already in library).
Confirmed no-action for now but should be verified with a fresh scan on an author with
known unimported files.

### Download client state

- **qBittorrent**: 71 items returned at every poll cycle. Items are largely seeding
  ebook and audiobook downloads. Path remapping is working correctly for all items.
- **SABnzbd**: 0 items returned at every poll cycle. Either no active Usenet downloads
  or the connection is idle. No errors observed in logs.

### Runtime configuration

**Finding 3-C (LOW)** — `config.xml` has `<Branch>develop</Branch>`. This means the
built-in updater (when enabled) will track the `develop` branch rather than `main`.
For a production instance, `main` provides more stable release-cadence tracking.
Update the changelog entry for v1.1.0 notes the default is being changed to `main`
for new installations but existing users retain their setting.

## Domain 4: Security

### Strengths

- **Dockerfile**: Non-root user (`uid 1000`, `/bin/false` shell), SHA-verified Node.js
  tarball, pinned base image digest. Excellent supply-chain posture.
- **SecurityHeadersMiddleware**: Full CSP with `default-src 'self'`,
  `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`,
  `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy` covering
  camera, microphone, geolocation, payment.
- **Kestrel**: `MaxRequestBodySize = 50 MB` set — protects against unbounded upload OOM.
- **Secrets management**: No hardcoded credentials anywhere in source. `docker-compose.local.yml`
  uses `${VARIABLE:-}` shell-injection pattern with explicit documentation.
- **API binding**: All `POST`/`PUT` endpoints use explicit `[FromBody]`/`[FromQuery]`
  source binding per the `check_http_binding.sh` enforcement script.
- **SQL**: Dapper parameterized queries throughout. No string-concatenated SQL.

### Findings

**Finding 4-A (MEDIUM)** — CSP includes `style-src 'self' 'unsafe-inline'`. This permits
style-injection vectors. Long-term mitigation is extracting inline styles to CSS files,
but this is a large frontend change. Acceptable risk for current phase; flag for Track E.

**Finding 4-B (LOW)** — CSP includes `'unsafe-eval'` for debug builds. Confirm
`SecurityHeadersMiddleware` uses `IHostEnvironment.IsDevelopment()` to gate this and it
is never included in Release artifact builds.

**Finding 4-C (INFO)** — `config.xml` contains the live API key for the running
instance. This file is in the data directory (`/home/swartdraak/.config/Bibliophilarr/`),
not the source repository, which is correct. Ensure this path is excluded from any
backup or snapshot tooling that might expose it.

## Domain 5: Backend architecture

### Strengths

- Provider abstraction: `IMetadataProvider`, `MetadataProviderOrchestrator` cleanly
  isolate provider logic. Hardcover, OpenLibrary, and fallback paths are independently
  replaceable.
- Exception handling in provider HTTP paths includes try-catch with appropriate logging.
- All 47 FluentMigrator migrations are reversible. No destructive schema changes without
  explicit Down implementations.
- Polly 8.5.2 is present and available for circuit breaker and retry policy use.

### Findings

**Finding 5-A (MEDIUM)** — Approximately 30+ sync-over-async `.GetAwaiter().GetResult()`
sites remain across `HttpClient.cs`, `RssSyncService.cs`, `BookSearchService.cs`,
`DelugeProxy.cs`, and others. The ROADMAP notes this as assessed and acceptable.
Risk is low in current single-instance use but flagged as a candidate for Phase 7
async modernization.

**Finding 5-B (MEDIUM)** — No retry budget or circuit breaker at the `MetadataProviderOrchestrator`
level. Individual provider calls are wrapped in try-catch but a systematic circuit-breaker
for provider failure streaks would prevent cascading load during provider outages.
Polly is already available — this is a single focused PR.

**Finding 5-C (MEDIUM)** — `CancellationToken` is not propagated from search commands
through to provider HTTP calls. Not a safety issue in current use but would improve
responsiveness during forced command cancellation.

**Finding 5-D (MEDIUM)** — `FluentValidation` 9.5.4 is 6 years old. Current release
is 11.x. API changes are breaking. Upgrade is tracked as DMQ-015 but has not been
started. With .NET 10 migration in Phase 7, this should be coordinated as
FluentValidation 11.x supports .NET 8 and above.
